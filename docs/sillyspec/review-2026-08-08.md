## 二、待决策项（不适合裸 quick，需走 brainstorm/plan 完整流程）

### 【P0】DB 并发写无锁 + tmp 名无 PID → 多 agent 并发 --done 丢进度/崩

- **位置**：src/db.js:107（tmp 名固定 `sillyspec.db.tmp` 无 PID）、_atomicWriteSync 105-118、transaction 58-75
- **问题**：DB 专属原子写 tmp 名无 `process.pid`（与 fs-atomic.js 的 `.${pid}.tmp` 不一致）；全仓 withFileLock 仅护 QUICKLOG/plan.md，DB 写入无文件锁串行化。
- **触发**：多 agent 并发各跑 `--done`，两 ProgressManager 进程同时 `_save` 同一 sillyspec.db：tmp 互覆盖 → last-writer-wins 丢进度；或 rename 撞 ENOENT 崩。
- **影响**：进度库数据丢失/状态分裂，违背项目"多 agent 并发"立身前提。
- **决策建议**：① 最小修（可 quick）：tmp 名加 `.${pid}` 对齐 fs-atomic；② 治本（架构级，走完整流程）：给 DB 读改写套 withFileLock 或换 better-sqlite3/LMDB。

### 【架构/性能】_write export-on-write + gate-status 无条件重复写

- **位置**：src/progress.js:382 `_write`、:475 `_updateGateStatus`；src/db.js:58-75 `_save`
- **问题**：每次 `_write` = 315KB 整库 export + ~5 次 fs op；`_updateGateStatus` 跟在每次 `_write` 后无条件重写 gate-status.json（单条 `--done` 估 3-5 次 `_write`，产物只被下次 hook 异步读，纯冗余）。
- **决策建议**：lazy 化子项（`_gateStatusDirty` 标记 + 退出前 flush 一次）可走 quick；DB export-on-write 是 sql.js 固有，换引擎属架构级。

### 【驾驭 F2】status / state / progress 三重语义冲突 + skill 命名反转

- **位置**：src/stages/status.js（3 步项目快照阶段）、.claude/skills/sillyspec-status/SKILL.md（路由到 run status）、.claude/skills/sillyspec-state/SKILL.md（路由到 progress show）
- **问题**：`sillyspec:status` skill description 承诺"显示阶段/步骤/变更"，实际路由到要干 3 步活的 status 阶段；真正秒查的 `progress show` 反挂在 state skill 下。self-audit #10 点名"status/state/progress 三套并存"但未处理。
- **影响**：高频入口（查状态）系统性把人导向重流程，浪费 token、污染进度库（progress show 里 default 卡在 status 阶段即物证）。
- **决策建议**：影响面广，走 brainstorm/plan。倾向：查进度统一指向 progress show；status 阶段改名 snapshot 或降级为内部辅助阶段。

### 【驾驭 F3】Windows DB teardown libuv 断言 → 退出码污染 127

- **位置**：所有"开过 DB 后报错退出"路径（如 `run brainstorm --done` 无 change、`run auto` 无 change）
- **问题**：进程 teardown 触发 libuv 原生断言（UV_HANDLE_CLOSING），退出码 127 而非 1（实测 `run brainstorm --done` 无 change、`run auto` 无 change 均崩；未知命令才正常 exit 1）。
- **决策建议**：收尾处先释放 DB 句柄再 exit，或统一 `process.exitCode=1` 让事件循环 drain。需补 Windows CI 用例。
