| 阶段 | R9 | R10 | R11 | R12 | R13 | R14 | R15 | OS 均值 |

读法：

1. **brainstorm+plan 是 SF 独有的固定税**：每次 10-16M，OS 对应物（proposal/specs/tasks 生成）只要 0.4M。R12 用输出纪律把它砍半（3.7+2.1M），是唯一例外。
2. **execute 一路膨胀**（16.8→45.6M）：任务相同，膨胀来自会话变长（O(n²)）+ 产物变厚（测试 15→37 例、文档 791→1302 行）+ Stage Review 仪式。OS 的实现段钉在 15-25M。
3. **verify 的墙钟被门禁策略主导**：71min（全量）→72min（死）→23min（module 化）→63min（R13 配额拖延）→R15 的 40+min 里大头是实验配置错误的自愈。token 上 verify 稳定在 14-29M——评审层不便宜，但它抓了 R14/R15 共 5 个真 P1。
4. **burst 只减往返不减 token**：R13 每阶段 run 调用 ×2-×4（R9 为 ×6-×19），token 反而创新高。
5. **R12 是被中断的全系列最优样本**：三生产阶段全部最低，均轮上下文 134K。

## 五、结构性发现（阶段级证据汇总）

1. **成本主项是 execute 段的 O(n²)**：R15-SF execute 45.6M/173r/均 263K——单阶段占全流程 53%。阶段断崖（R15 二会话）已证明拆会话立竿见影（均轮回落 ~120-170K），但只覆盖了 verify。
2. **SF 的两大固定税 OS 都没有**：brainstorm+plan（10-16M）和 verify（14-29M）。OS 的钱几乎全花在实现上（15-25M/101-118r，三轮几乎复刻）。
3. **已被验证有效的三个减负手段**：门禁 module 化（verify -68% 墙钟）、输出纪律（R12 三阶段全最低）、子代理范围约束（R14→R15 子代理 8.3M→1.9M）。
4. **已被验证无效的手段**：burst（往返↓ token↑）、green-cache（命中场景少：R15 二会话仍全跑）。
5. **待修工具缺陷**：verify deps 门禁在隔离沙箱重建环境不带 `--extra dev`（R14-R15 各咬一次）；收口"产物没落盘"类硬拦连击（R15 execute 收口连挡 4 次）。

## 六、下一步（按预期收益排序）

1. **按阶段拆会话（stage-runner）**：把断崖的效果推广到 brainstorm/plan/execute——预计砍掉 execute 段一半以上回放，是唯一能把 SF/OS 比从 4-5× 拉回 2× 的杠杆。
2. **输出纪律固化**（R12 路径）：把"长输出重定向+tail 回看"写进各阶段说明书铁律，目标把均轮上下文从 215K 压回 140K 档。
3. **修 gate 隔离环境装配**（`--extra dev`/`--all-extras`）+ 收口拦截改一次性清单（工具侧 quick）。
4. **实验配置模板**：local.yaml 前端命令必须点名 vitest 文件（R15-SF verify 的 40 分钟自愈不该重演）。
5. **消费端修复清单**（§7.2 审计产物，任一侧实现入库前处理）：detail 大小上限一行约束；归档 spec"全量"文本对齐实现；alembic revision id 双侧撞号（`20260924090000`）重编。

## 七、verify FAIL 剖析与 OS 交叉审计（2026-09-24 夜补）

> 本节为收官补充：①两次 FAIL 的 5 个 P1 代码级定位与成因分类；②用同一把尺子交叉审计 OS 两版实现（此前 OS 侧从未被对抗审查过）；③"OS 代码质量更好？"的三层判定；④R14→R15 差距 2.9×→5.5× 的算术分解。

### 7.1 R14/R15-SF 五个 P1 的定位与成因

| P1 | 代码锚点 | 缺陷机理 | 成因维度 |
|---|---|---|---|
| R14-P1-1 多工作区同名合并 | `list_change_events` union 读（service.py ~1985）：`ws IN (可见集) AND change_name`，同名 change 时间线跨工作区合并 | 作用域消解缺失 | 作用域（测试全单工作区） |
| R14-P1-2 并发剪枝多删 | `_prune_observation_events`（service.py ~1849）：count→选 victim→delete 三句非原子，并发双写超删 | 并发窗口 | 并发 |
| R14-P1-3 OpenAPI 漂移 | 路由描述改后未重跑 `gen:types`，openapi.json/api-types.ts 与实现不一致 | 产物同步 | 生成物失同步 |
| R15-F-01 乱序永久丢失 | 服务端 `event_ts >= since`（service.py ~2102）× 客户端游标=累计集最大 ts（tsx ~108）：晚到的早 ts 事件永久滤除；一条未来 ts 把游标推到未来则后续全不可见 | 契约宣称 at-least-once（D-005@v2）实现不兑现 | 乱序到达 × 契约落差 |
| R15-F-02 切换串台竞态 | 修复提交 `82f254128` 只重置 2/4 个 ref（漏 `autoDecidedRef`/`userOpen`）+ `queryFn` 未接 AbortSignal，旧变更在途请求完成后写入新变更状态 | 上一次修复的不完全 | 生命周期竞态 |

### 7.3 "OS 代码质量更好？"——三层判定

| 层面 | 判定 | 依据 |
|---|---|---|
| 代码工艺 | **平手** | 同分层约定、同认真度；两边 service 逐行读均在水准上 |
| 设计取简 | **OS 略优** | 全量重拉结构性消灭 F-01/F-02 整类 bug（不是修得好，是没走进去）；不立兑现不了的承诺。SF 增量方案省带宽的代价=2 个高危 P1+121 轮 verify |
| 交付确定性 | **SF 机制完胜** | OS 的"通过"是**未审的通过**（一遍交叉审计即翻出 6 项）；SF 出厂态 bug 更重但全部已知、拦截、带移交清单，且两次拒绝凑 PASS |

结论：OS 的"干净"观感 = 取简 + 没人看 + 产物薄对不上账的地方少——**不是质量更好，是简单且未受检验**。OS 的"通过"与真实缺陷之间隔着一次没人做的审查；SF 的 FAIL 与真实缺陷之间隔着一行修复。目标形态是 OS 式取简 + SF 式审查的组合。
