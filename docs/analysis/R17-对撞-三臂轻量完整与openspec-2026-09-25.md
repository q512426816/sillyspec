## 四条结论

1. **R15 爬坡病复现＋解药实证（本实验核心数字）**：同任务下完整流程 16.44M vs 轻量 2.11M——**7.8 倍**，
   复现原版「SF 完整流程 token 远超 OS」（86M/18.5M≈4.7 倍）的病；而轻量道把 token 压到 OpenSpec 水平线
   （低 8%）——thin 化解决了 R15 系列六轮优化没压下来的曲线。
2. **质量面三臂无区分（诚实记录未复现）**：R15 原版 SF 拦 2 P1/OS 放行的质量差在 R17 未复现——本任务边界
   三臂全接住。结构性差异仍在（臂2 拦截均为设计内质量门 vs 臂1 validate 只查工件格式），但本样本无 P1 可拦。
3. **摩擦面反转**：臂3 的 7 次拦截中 2 次是 sillyspec CLI 自身 bug（--same-session 未登记 knownFlags——
   complete.js:1748 消费但 command.js 允许清单缺失；verify 批量快进与 noAI 亲测步互锁需四步绕行）——
   完整流程的复杂度本身制造摩擦；轻量道把 CLI 复杂度暴露面一并缩掉（臂2 的 2 次拦截都是设计内门）。
4. **验收器自我纠错插曲**：B1 探针初版踩进 SPEC 自身歧义（「id 永不复用」vs 括注「max+1」在删最大 id 场景
   矛盾），误判臂1 FAIL 后修正探针重跑——规格歧义是常态，验收器也要接受被审。
