## 二、SF 侧提示词（sillyspec，最新版）

```
【角色】你是执行代理，用 SillySpec 流程完成下面的任务，走到归档为止。

【环境】
- 工作目录：r16-sf-observation（独立 worktree，基线 53a5c5c9d，与主仓隔离）
- 依赖已预装：后端 uv 环境已带 dev extra（aiobotocore/mypy 可用，uv run pytest 直接可用）；前端 node_modules 已装
- sillyspec 为最新版；local.yaml 已配好（后端定向测试 + module 策略 + 2400s 超时；前端全量留 CI）

【流程要求】
- 严格按 CLI 指引走：入口 flow start，把任务与成功标准完整放进 --input
- CLI 的清晰度门/复杂度预判给什么建议就执行什么（升厚是正常机制，不要人为绕过或拦截）
- 收口只认 flow done 的裁决；被拒就按提示修复重跑，不绕门

【任务】为平台实现「观测事件（observation events）」服务。这是同族任务第三次独立实现——不要去找旧实现参考，独立设计。

后端（FastAPI + SQLAlchemy + alembic）：
1. 新模块 observation：事件批量写入端点（单批上限 500 条）与查询端点
2. 写入鉴权：仅 shpsync_ token 可写；workspace 一律从 token 派生（body 不收 workspace 字段，无归属 403）
3. 事件模型：type/rule/detail(dict)/event_ts/received_at/provisional 等字段；去重键对 tz 规范化后的业务字段逐字节稳定；重复写入按 IntegrityError 回滚重试收敛
4. 查询：scope=token 可见工作区；since 增量参数；服务端窗口上限（行数上限与 detail 单行大小上限自定并写明）；(event_ts, id) 双列稳定排序；truncated 标记
5. provisional 事件零业务判定红线：写入路径不读 changes 表、不改任何变更状态
6. alembic 迁移一条（revision id 用当前时间戳，勿与既有迁移撞号）
7. openapi.json 与前端类型生成物（gen:types）同步提交

前端（Next.js）：
8. 变更详情页观测事件轮询组件：30s 轮询；新 warning 事件自动展开一次（用户手动收起后不再自动展开——展开决策只发生一次）；切换变更时全部状态 ref 清零、在途请求接 AbortSignal 取消

测试与承诺：
9. 后端 pytest 覆盖：写入鉴权/批量闸/去重收敛/窗口与排序/since 边界；前端 vitest 覆盖：轮询/展开决策/切换清理（定向跑，不全量）
10. 明确写出你承诺的交付语义（如 at-least-once 或更强），实现必须兑现承诺——收口评审会拿承诺逐条对代码（乱序到达/并发写/切换/多工作区作用域四个维度）

成功标准：
- 上述 1-9 全部实现且定向测试全绿；alembic 迁移可执行；openapi/gen:types 与实现对齐
- 每条承诺（含交付语义、窗口上限、展开决策语义）在实现中兑现且可指认

【纪律】
1. 输出纪律：预计输出超过 50 行的命令（pytest/vitest/安装/构建）一律重定向落盘（> .runtime/logs/<名>.log 2>&1），只回看 tail -n 50；禁止把全量输出读进上下文
2. 子代理纪律：勘察类子代理必须给定明确范围与产出上限（一段摘要），禁止无界自由探索
3. 禁全量测试：除任务定向测试外全量套件一律不跑（留 CI）；基线预存失败登记绕开，不修别人的测试
4. 全程本会话完成（除非 CLI 明确要求交棒）；不自行 fork 会话
5. 提交用显式 pathspec，禁目录级 git add

【计量】不要手工记录 token/时间——事后从 db.sqlite 与 .sillyspec/.runtime/flow-telemetry.jsonl 切片。
```

## 四、测量口径（与 R8-R15 一致）

- 数据源：zcode db.sqlite（model_usage 按轮 / part 按工具调用），DeepSeek 定价
- 阶段锚点：SF = flow start / flow done 时间戳 + flow-telemetry.jsonl（记录实际走的道、协议调用数、是否升厚）；OS = openspec new change / 首次文件编辑 / openspec archive（R8+ 附录方法）
- 判据表：

| 指标 | R15-SF 基线 | R16 判定线 |
|---|---|---|
| 全流程输入 | 86.1M | ≤50M 达标 / ≤43M 优 |
| SF/OS 成本比 | 5.5×（去坑 4.2-4.6×） | ≤2.5× |
| 墙钟 | 109min | ≤70min |
| 质量面 | FAIL 拒归档（正确） | 收口评审照常；盲维四问是否被 design 槽/绑定槽抓住（F-01/F-02 同型缺陷不得再犯） |
| 资产面 | — | FR 测试绑定条数、patch 留档零泄漏、FR 发号提升条数（薄道新增三件全要产出） |
| 协议调用 | 30-80 次 | thin 臂 ≤5 次（start+done±重跑） |

- 失败判据：任一 P0 项无改善 → 对应机制回滚/降级，对账文档补归因（各条目独立开关）。

## 五、与 R15 的口径差异点（如实记录，不藏）

1. R15-SF 的「主会话 execute → 手动交棒 → 二会话 verify」在 R16-SF 由薄道单会话取代（升厚则重现阶段断崖提示，由 agent 自行决定）；
2. R16-SF 的 local.yaml 由模板预置（R15 是会话自愈 40 分钟收敛出来的——环境账不再混入流程账）；
3. R14/R15 的消费端修复清单（detail 上限/received_at 游标/spec 文本对齐）尚未入库基线——R16 两臂在同一未修基线上跑，公平。
