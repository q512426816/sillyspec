## 何时使用

- 用户报告 bug / 异常 / 偶发问题 / 性能回归，要求排查或修复
- bug 类轻量变更动手前（先诊断后动码——诊断产物直接成为变更证据）
- 你发现自己准备「看几眼代码就猜根因」时——那正是本 skill 要拦的失败模式

## 核心思想

「先建一条跑得红的复现命令」是「先写测试后写实现」在诊断场景的同构物。agent 修 bug 的典型失败：读代码 → 锚定第一个看似合理的假设 → 改 → 碰巧绿 → 收工（实际根因未除，改天复燃）。反馈回路先行（red-capable 命令在场）让每一步假设都可证伪。

## 五阶段 gated 诊断环

每阶段有硬 gate：**前一阶段产物未落定，禁止进入下一阶段**。

### Phase 1 — 复现回路先行（gate：命令跑红过一次）

建一条 **red-capable 复现命令**，必须同时满足四条件：

1. **确定性**：重复跑结果稳定（偶发问题用循环/条件放大到确定触发，不行则记录触发概率与放大手段）
2. **秒级**：单次运行在秒级返回（分钟级回路会让后续每轮假设验证都变慢）
3. **agent 可独立跑**：一条命令（脚本/单测/HTTP 调用均可），不依赖人工点击或不可控外部状态
4. **对准本 bug 变红**：命令的失败输出指向所报症状，不是别的问题

**gate：没有跑红过一次的复现命令，禁止读业务代码建根因理论。** 看代码可以（定位入口），下结论不行。

### Phase 2 — 最小化 repro（gate：减到不能再减）

在复现命令上逐段裁剪：无关参数、无关数据、无关步骤——每裁一段重跑一次，症状消失就恢复该段。产出：最小复现输入 + 「少了 X 之后症状消失」的边界记录（X 往往就是根因的邻居）。

### Phase 3 — 可证伪假设排序（gate：每条假设带预注册的证伪条件）

列 3-5 个假设，每条必须写成可证伪形态：**「若假设 H 为真，则在 <具体位置> 观察到 <具体信号>；观察不到则 H 证伪」**。按嫌疑排序逐个验证——一轮只验一个，禁止并行改多处（改了三处绿了不知道谁起作用）。

### Phase 4 — tagged 插桩（gate：探针带标、即插即清）

需要内部信号时才插桩。临时日志/断点必须带 `[DEBUG-<id>]` 唯一前缀（口径同 execute 阶段「临时调试日志唯一前缀」铁律，一次排查一个 id）——收尾按前缀 grep 清零。插桩只服务当前假设的验证信号，不留存。

### Phase 5 — 修复 + 回归锚定（gate：红转绿 + 回归测试在场）

1. 最小修复（只改根因，不顺手重构——重构归后续变更）
2. 复现命令重跑：红 → 绿
3. 把复现命令固化为回归测试锚进测试套件。**变异自证**：临时改坏刚修的代码确认该测试真的会红（diff 干净副本确认变异生效），再改回——防「测试构造性通过」
4. 清全部 `[DEBUG-<id>]` 探针，`grep` 清零确认

## 与 SillySpec 流程的衔接

- **bug 类轻量变更**：`flow start` 的成功标准里写复现命令（「- 复现命令 `<命令>` 从失败转为通过」）——收口实测门会跑它，机器门给诊断纪律兜底
- **收口优先序**：变更测试面里复现命令转绿的回归测试是修复成立的直接证据
- **防复潮**：修复后把「根因一句话 + 复现命令」distill 进 knowledge（同类症状下次可检索命中）
- 本 skill 不替代流程——诊断发生在变更内，产物（复现命令/回归测试/根因记录）随变更归档

## 反模式（每个都有 tell）

- **读码即诊断**：tell——你已说出「应该是 X 的问题」但复现命令还不存在。回 Phase 1
- **广撒网修改**：tell——一次 diff 触及 3+ 处可疑点。回 Phase 3 一轮一假设
- **假灵敏度**：tell——回归测试从没红过就直接绿。Phase 5 变异自证没做
- **探针残留**：tell——收尾 grep `[DEBUG-` 有命中。清零再交付
