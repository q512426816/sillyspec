# 设计记录（Design Record）— 2026-10-20-thin-user-decision-record

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

三个触点全是文案级注入、零新机制：① src/flow.js 全新 start 横幅 lines 数组在任务面块与三断点纪律之间加一行执行期用户决策落盘纪律行（含 decisions add 命令样例与承诺面同步提示）；② 同文件断点②行文追加对账半句（保留既有句与「执行断点」关键词）；③ src/task-tick.js runTaskTick 回显尾部按 decisions.md 存在性 gating 一行提示——与既有「spec 面未就位」现场提醒（2026-10-19-approve-gate-tick-nudge）同款 advisory 形态：existsSync 判定、纯提示、try/catch 静默降级。

选文案注入而非机器门的理由：CLI 看不见会话，「用户说过而 agent 没记」是纯沉默面，漏记不可检测，门禁无从建起（假门禁不做）；而横幅行有 thin-order-canon 实证背书（措辞改变行为经时间戳还原+14 例抽样验证），task tick 是执行期对 agent 最高频触点，断点②是向用户汇报的自然对账时刻——三触点把记忆钩子放在离事件最近的位置。决策落盘通道本身零新增（decisions add → upsertDecision 单一写入者已存在且带格式白名单）。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

CLI 签名与数据格式零变化。三处均为 stdout 文案追加：`flow start`（新建）横幅新增一行、断点②行文追加半句（「执行断点」关键词保留，flow-checkpoints 的 /执行断点/ 断言兼容）；`task tick` 回显在 decisions.md 缺席分支条件新增一行，在场分支输出逐字节不变。无新 flag、无新子命令、无文件格式变化。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

成立。三触点只依赖 decisions.md 当前存在性这一磁盘事实，无时序假设；tick 在未批准/已批准任意阶段触发提示判定都成立，与既有 spec 面提醒并列共存互不干扰。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

三触点对盘面只读（existsSync），零写盘；真正的决策写入走既有 `decisions add` → upsertDecision 原子写（同 id 幂等整块替换），并发安全面不在本变更改动范围内。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

安全。横幅行属首进面：中断后 resume 走恢复简报（不含新纪律行，纪律不丢由既有红线重申机制覆盖）；tick 提示无状态，每次按盘面即时判定，重入无残留态。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

不会。提示行内 change 名取自本次调用参数，判定只读本变更目录下 decisions.md；多变更并行时各自 tick 各自判定，互不引用。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险=提示噪音：decisions.md 缺席期间每 tick 都出提示——自限：agent 记一条决策文件即在场、提示消失；全程无用户决策时提示属轻度噪音，advisory 可接受。试过但放弃：a) 收口硬门拦 decisions.md 缺席——缺席合法是轻量道刻意设计（槽4收割/decisions add 懒创建），且漏记本身不可检测，门是假的；b) 决策内容自动捕捉——CLI 看不见会话，做不到；c) resume 恢复简报同注入纪律行——恢复简报职责是读盘面报进度，加新纪律行与恢复面形态冲突，断点续跑纪律已由红线重申机制承载。
