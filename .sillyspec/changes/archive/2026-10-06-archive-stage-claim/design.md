## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

把 runArchiveChain 内「补暂存源侧移动」的 minePaths 批处理循环抽成导出助手 `stageArchiveSourceSideMoves({ cwd, paths })`：逐批 `safeGit(cwd, ['add', '--', ...batch])` 后**校验返回的 error**（safeGit 契约是返回 `{value, error}` 不抛错——忽略返回值即吞错），失败收集 `{path, error}` 明细，返回 `{ ok, count, failures }`。文案渲染独立成导出函数（成功文案维持既有逐字不变；告警文案列失败路径与 error 首行 + 手工兜底指引），runArchiveChain 按结果择一打印。

选这个方案是因为它只加「结果校验 + 分支打印」，暂存语义与批处理（chunkPaths 防 Windows argv 上限）零变化；测试通过导出助手直接断言两半（返回值 + 文案），无需驱动整条归档链。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

- `src/run/complete-handlers.js` 新增导出 `stageArchiveSourceSideMoves({ cwd, paths })`（返回 `{ok, count, failures}`）与文案渲染导出；runArchiveChain 的 minePaths 段改为调用助手并按结果打印。
- 行为可见面：add 失败时归档链输出从「假成功提示」变为 ⚠️ 告警（含手工兜底指引）；成功路径输出与现状逐字一致。CLI 命令、文件格式：无变化。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？
   不适用——单次批处理调用，输入是既定路径清单，无事件序问题。
2. 并发写：两个执行体同时操作同一数据/文件会发生什么？
   add 与他进程写 index 的竞态（index.lock）正是本变更要诚实暴露的失败面——失败不再被吞，告警 + 手工兜底指引；重跑幂等（归档子步断点续）。
3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？
   安全——助手无跨调用状态；失败不抛错不阻断归档链（fail-soft 与现状一致），部分成功批的暂存保持在场（幂等 add 重跑同值）。
4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？
   不会——cwd 显式传入，只 add 调用方给的路径清单（minePaths 已按本变更目录名过滤）。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：告警面打扰——add 失败从静默变告警，若失败高频（如持续锁竞争）会重复提示。可接受：假成功比告警贵（实测已付出一笔手工补提交）；告警自带兜底指引可执行。
放弃的方案：①让 safeGit 失败时抛错（改公共错误语义）——放弃，影响全部调用方，超本变更刀口；②失败时自动重试 add——放弃，锁竞争类失败的重试时序不可控（此前已实证 add 竞态即现即逝），诚实暴露 + 人工重跑更稳。
