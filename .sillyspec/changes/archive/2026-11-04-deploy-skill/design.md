# 设计记录（Design Record）— 2026-11-04-deploy-skill

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。
单文件新增 `.agents/skills/deploy/SKILL.md`，内容全部来自 2026-11-04 的 3.34.1 真实发布执行（暂存区 10 文件归属判别、quick-retired R5 精确锚同步、lint 1111+锚点 8/8 验证门、sillyspec push 快进直推、npm PUT 202 异步受理→curl 直查 dist-tags 核验），按 skill-creator 规范（imperative+解释 why+示例+速查表）固化。选址 `.agents/skills/`：ZCode 项目级发现面（跨工具标准位）且随 git 入库；不选 `.zcode/skills/`（被 .gitignore，不入库团队拿不到）、不选 `.claude/skills/`（产品交付面——维护者技能不随 npm 包发给消费者，且会混入 sillyspec-* 产品技能命名空间）。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？
无代码接口变化。新增一个 SKILL.md 文档资产（frontmatter name=deploy+description 触发词组）；对 ZCode 会话可见——用户说发布/deploy/发版类词汇时触发；npm 包体积影响 = 该单文件（~4KB，pack 无 files 白名单会带入，可接受——注：不引入 .npmignore，它会整体取代 .gitignore 的打包排除语义，风险大于收益）。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？
   不适用——纯静态文档，无时序面；skill 触发由 harness 元数据匹配，与文件写入时序无关。
2. 并发写：两个执行体同时操作同一数据/文件会发生什么？
   单文件单写入者；并行会话同时改 skill 的概率极低，git 提交面按显式 pathspec 隔离不夹带。
3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？
   安全——文档常驻无状态；skill 内容迭代走本仓正常变更流程。
4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？
   不会——description 显式限定「只适用于本仓（sillyspec）的 npm 发布，不适用于消费仓」，防在用户仓误触发。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？
最大风险＝skill 内容随流程演进过时（如 registry 行为变化、锚点测试改名）——缓解：坑清单速查表每行都钉了「症状→真相→处置」三段可验证结构，过时条目在下次真实发布时立刻暴露，随发布顺手修。放弃方案①：把流程做成 scripts/ 自动化脚本——否决，发布含多处人判断点（版本号确认、暂存件归属、既有红处置），全自动会把判断错处放大成不可逆 npm 发布；skill 让 agent 带着坑清单执行恰好把「半自动+留痕」固化。放弃方案②：放 .claude/skills/ 随产品分发——否决，见做法概述（交付面污染）。
