# 设计记录（Design Record）— 2026-10-15-jsx-batch-cmd-chunk

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

在 verify-postcheck.js 的 buildDepsBatches 内加模块私有 chunkByCommandLength(prefix, files, maxLen=6000)，对 deps(auto-js)（node --test 原生）与 deps(auto-jsx)（vitest/jest 项目运行器）两批按「命令前缀 + 逐文件参数拼接总长」分块：累计超 6000 即切新块。单块保持原批名（行为零回归）；多块命名 deps(auto-js|jsx:N/M) 独立计账（count/files/dropped 归块 0）。选命令长度分块而非文件数分块：上限的真实约束是字符数（Windows cmd ~8191），文件名长方差大（本仓实测含 100+ 字符的带引号路径），按字符预算最贴约束且跨平台保守（POSIX ARG_MAX 充裕，多分块仅多几次 runner 启动）。补丁由消费仓并行会话 2026-10-15-zcode-engine-appserver 实施（跨仓事故驱动最小修复），本变更收口登记并补行为面单测（test/dynamic-batch-chunk.test.mjs，3 用例：单块零回归/多块 N:M 守恒/js 原生同款）。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

新增模块私有函数 chunkByCommandLength（不导出，经 buildDepsBatches 行为面测试）；buildDepsBatches 对外签名不变。可见行为变化仅一处：当 js/jsx 批拼接总长超 6000 时，产出多个批（deps(auto-js:1/2)…）替代单批——批名从字面量变为含分块序号；其余路径（单块）逐字零回归。CLI 端点/命令/文件格式：无变化。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

1. 乱序/迟到到达：不适用——buildDepsBatches 是纯函数，输入 deps/changedFiles 顺序决定块内顺序，分块保持输入序（稳定切分），无乱序到达面。
2. 并发写：不适用——无共享可变状态（chunks 局部数组）；多进程各自调用互不影响。
3. 切换/生命周期：批对象生命周期与一次 verify 实测一致，块与失败账本按批名记账（:N/M 独立计账），中断重跑按块归因不串。
4. 作用域：纯内存计算无落盘；maxLen 全平台同值 6000（保守统一，避免平台分叉配置面），跨仓调用同函数无串台。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：maxLen=6000 对极短前缀+超长单参数（Windows 单路径组件上限 255，理论单参数 <300 字符）恒安全，但对自定义超长前缀（如极深 cd 链）的批未覆盖——当前调用面前缀均 <100 字符，风险可忽略。试过放弃：①按文件数分块（如 50/批）——文件名长方差大（60~120+ 字符带引号），数帽不能保证字符上限，放弃；②跨仓通用 argv 文件清单通道（vitest 无 stdin 文件清单原生支持）——侵入 runner 协议，超出最小修复范围，留待上游。
