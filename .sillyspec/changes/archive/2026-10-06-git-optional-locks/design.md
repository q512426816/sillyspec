## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

在 git-helper.js 的两个 exec 点（safeGit:102 / git:131）统一注入 `GIT_OPTIONAL_LOCKS=0`：env 构造为 `{ ...(opts.env || process.env), GIT_OPTIONAL_LOCKS: '0' }`。该开关是 git 官方为后台/只读工具设计的——只禁「机会性」锁（status/diff 等读命令顺手刷新 index 写回时要抢的 index.lock），真写命令（add/commit）的必需锁不受影响（实验实证：带 0 的 add+commit 正常）。经公共入口的全部调用（含 gitQuiet→git 委托链、watcher 3s 轮询、spec-sync 后台）自动获得非锁行为，单点修复全覆盖。

选这个方案而不是逐调用点加 `--no-optional-locks` flag：flag 要逐命令插且只影响单调用；env 在公共 exec 点一次注入即覆盖所有子命令，且不枚举「哪些命令是读」——开关本身由 git 语义安全分派（机会性 vs 必需），不是自建白名单。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

- `src/git-helper.js` `safeGit`/`git`：子进程 env 统一追加 `GIT_OPTIONAL_LOCKS=0`（与调用方 env 展开合并）；签名不变。
- 行为可见面：CLI 自建 git 子进程不再机会性改写 `.git/index`（读路径零锁窗口）；并发 git add 不再被本工具的轮询干扰。写命令行为不变。绕过 git-helper 的本地 exec 点（commit-guard hook、gate-snapshot 等）不动。
- CLI 命令、文件格式：无变化。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？
   不适用——env 注入是每次子进程 spawn 的独立属性，与调用顺序无关。
2. 并发写：两个执行体同时操作同一数据/文件会发生什么？
   本变更正是并发写维度的修复：本工具的读轮询不再持 index.lock，与外部写（用户 git / IDE / 并行会话 add）的锁冲突面收敛为「真写 vs 真写」——git 自身的锁串行化语义覆盖；真写冲突时后到者照旧报错（既有行为，非本变更面）。
3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？
   安全——行为差异只在「读命令是否顺手刷新 stat 缓存」；index 内容语义不变，中断/重跑无累积态。
4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？
   不会——env 只作用于 CLI 自己 spawn 的子进程，进程边界即作用域边界；不影响用户 shell 里的 git。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：读命令不再刷新 stat 缓存，后续读每次都要重扫文件 stat——大仓上 status 略慢、index 文件 mtime 不再被本工具更新。可接受：正确性无差（status 结果仍如实反映工作区），性能差在毫秒级轮询场景不可观测。
放弃的方案：①逐调用点加 `--no-optional-locks` flag——放弃，只覆盖被改的调用点且维护面碎；watcher/后台全覆盖需要枚举改点，恰是要避免的形态。②在 stageArchiveSourceSideMoves 里对 lock 类错误做有界重试——放弃（本变更时点）：重试是下游补丁，治标；上游消灭锁窗口后本工具自扰的锁冲突已不存在，外部进程的偶发冲突由 archive-stage-claim 的告警面兜住。若外部冲突实测高频再议。
