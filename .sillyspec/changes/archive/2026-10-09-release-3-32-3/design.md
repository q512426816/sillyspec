## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

成立。版本号是静态标量，无顺序依赖；R5 锚与 package.json 同提交原子变更，不存在版本号与锚断言错位的中间可观测态（git 提交为原子单元）。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

他侧会话并行发版的窗口极小且 npm publish 对同版本号幂等拒绝（403 已存在），双发同号会撞墙而非双写；package.json 竞态由 git 工作区互斥承担。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

安全。版本面两文件为落盘态；中断于 push/publish 之间的窗口重跑同命令幂等（push 幂等、publish 撞已存在版本报错可判读），无半写状态。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

不会。版本号单一源在 package.json；发布操作单仓单包；消费仓经 npm 拉新版本，无串台面。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：npm publish 凭证/2FA 环节失败（本地 npmrc 有 always-auth 告警配置）——失败则重试或转用户处理，版本面提交与推送不受影响可先行落定。放弃方案①：发 3.32.4（用户口头版本号）——线上 latest 实为 3.32.2，跳 3.32.3 违反用户自己给的准绳「最小版本加一」，选 3.32.3 并在交付说明中向用户说明差异。放弃方案②：npm version patch 自动提交——自动提交不走本仓显式 pathspec 纪律，手工两文件编辑+显式清单提交。
