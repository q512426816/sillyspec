## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

横幅是静态 lines 数组按序渲染，无输入时序依赖；红线块位置由数组顺序保证——不适用。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

多会话并行各自 flow start 只打印不写盘（触发同步为既有 best-effort 后台面）；源码改动按显式 pathspec 提交隔离——不适用。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

断点续跑重入时首进横幅不重现、只出恢复简报——故简报必须带红线重申行，保证变更生命周期内规则不因重入而丢失（本变更补齐的正是这一环）。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

横幅与简报是 flow 命令专属输出，不进 MCP/平台协议面（watcher 事件只带 checkbox 状态），跨仓/跨工作区不串台——不适用。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险=横幅膨胀稀释注意力（现约 60 行，红线块若展开成段会更没人读）——用 3 行编号红线并同步压缩下方重复表述对冲（实测渲染行净 +2，已在增量可控范围；评审 P3 核正初稿「净行数不增」的误记）。死路：曾考虑让 `expandTaskShorthand`（sentinel-assertions.js）直接支持「task-01..task-05」区间展开——放弃：那是放宽反假完成收口门的判据语义，属门设计变更；用户实证报错清楚改起来快，痛点在知晓时点不在判据本身，前置告知即可不动门。
