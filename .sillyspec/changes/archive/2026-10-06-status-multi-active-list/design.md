## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

只改 src/run/command.js 只读短路 `!progress` 分支（READONLY_AUXILIARY_STAGES 唯一成员 status 的空态入口）：read() 无显式 --change 在「≥2 活跃变更」时与「零活跃」同样返回 null（src/progress.js:416-424 单活跃才自动推导），旧分支把两者一律当「无数据」打空态引导。修法：分支内先做库在场前置检查（existsSync pm._runtimePath(cwd,'sillyspec.db')，与 change-registry getChangeTitle 同款防 _ensureDB 建库副作用），在场则 pm.listChanges(cwd) 读活跃名，≥2 时打印「N 个活跃变更」清单（每行 existsSync pm._changePath 判目录，缺失标「本地无目录」）+ 可照抄的 --change 提示行后 exit 0；其余（0 活跃/库不在场/显式 --change 未命中且单活跃）维持原空态引导不动。选这个方案因为歧义发生在「选谁展示」这一层，read() 的单活跃自动推导语义不动、只读短路的零副作用承诺不动，是最小切口。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

无函数签名/文件格式变更。对外可见行为变化仅一处：裸 `sillyspec status`（无 --change）在进度库 ≥2 活跃变更时，输出从「未找到进度数据（只读查询不建变更）+ 空态引导」变为「N 个活跃变更清单 + --change 提示行」，exit 0 不变；0 活跃/库不在场/显式 --change 场景输出逐字不变。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？
   不适用：本分支是查询时点的只读快照（单条 SQL SELECT），无跨事件时序假设；清单内容即查询时刻 DB 真相，乱序不构成输入。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？
   SQLite 单读无锁竞争；并发的归档/删除把某行 status 改走最多让清单少列一行（查询时点真相），不误报、不抛错。listChanges 与后续逐行 existsSync 之间存在行被归档/目录被搬的竞态：行已归档则本清单多列一行（下次查询自愈），目录刚消失则如实标「本地无目录」——两向偏差都是展示级，无写路径可损坏。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？
   安全：分支纯读 + console.log 后立即 process.exit(0)，无中间状态落盘，中断点任意重跑幂等。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？
   不会：cwd/specBase 解析在进入本分支前完成（既有逻辑），listChanges/_changePath 均以该 cwd 为根；会话专属 worktree 场景下 status 只读短路不触发 spec 锚定改写（本分支晚于 worktree 锚定代码），读的是锚定后 spec 的库。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：幽灵行刷屏——DB 残留大量 status='active' 但目录早已不在的行时，清单较长且多数标「本地无目录」。可接受：这正是 DB 真相，且 doctor --cleanup-remnant 是既有清幽灵通道，本分支只负责如实展示。放弃的方案：①在 listChanges（库函数）里过滤无目录行——污染库语义，DB 行与目录存在性是两个真相层，别处依赖 DB 口径；②改 read() 让多活跃返回特殊值——动核心推导语义，调用方十余处，风险与收益不成比例；③清单截断加「其余 N 个略」——现实活跃数是个位数到两位数，截断只省屏幕不省正确性，反藏信息。
