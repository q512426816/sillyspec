## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

src/ui-visual.js 的 UI_TOUCH_PATTERNS 删去 /渲染/、/组件/、/样式/ 三个后端高频通用词（CLI「渲染输出」「组件」「输出样式」是常规后端用语——2026-10-05-knowledge-stats-freshness 实测「聚合函数+渲染+对应单删」即误触整段 UI 须知+探针 warn；本变更自己的 input 描述问题时又复触一次，自证误伤面宽）。既有正例五条各含第二信号（页面/前端/UI/视觉/tsx 扩展名）不受影响；误漏兜底走既有设计承诺「文件面扩展名兜底」（detectUiTouchInPaths）。src/flow-draft.js 模板头注加一行锚行防呆（四问/FR 标题锚从模板原样复制勿手打——2026-10-05 两度实证句号手写成问号被锚对比拒收）。

选词表收窄而非双信号分层（input 命中且文件面佐证才算）：分层会把纯文案改版的真 UI 变更（只改 copy 不动前端文件）漏掉，而收窄三词只损失「input 仅含渲染/组件/样式而无任何其他 UI 信号」的弱形态——该形态本就接近不可判定，扩展名兜底足够。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

- UI_TOUCH_PATTERNS 常量减三词（模块内私有，detectUiTouch/detectUiTouchInPaths 导出签名不变）
- 行为变化：input/规约文本仅含「渲染/组件/样式」而无其他 UI 信号的变更不再判 UI 触达（不再渲染须知段、探针 12 报不适用）；含页面/前端/UI/视觉/界面/布局/原型/截图/主题色/配色/前端扩展名的检测能力不变
- flow start 起草的 design.md 模板头注新增一行防呆文案（对已起草变更无追溯影响）
- 其余接口无变化

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

不适用：词表全仓同版本生效（detect 行为确定性），无 per-repo 状态串台面。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：误漏——真 UI 变更的 input 恰好只含「渲染/组件/样式」而无其他信号且文件面无前端扩展名（如纯设计讨论期）。缓解：flow start 须知本就是 advisory 非门禁（漏渲染只少一段提示），且 detectUiTouchInPaths 扩展名兜底覆盖绝大多数真 UI 交付；探针 12 的 error 档（降级无裁决）不依赖词表触发条件的变化。
试过放弃：① 双信号分层（input 命中 ∧ 文件面/多词佐证）——纯文案改版真 UI 变更会漏，且把简单启发式复杂化；② 全词表保留+对 CLI 仓加白名单——按仓配置引入 per-repo 维护面，与「仓中立」模块承诺冲突。
