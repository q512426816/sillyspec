# 设计记录（Design Record）— 2026-11-04-sync-fail-silent-fix

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

三处小修：① index.js platform sync 全树分支补 `r.ok === false` 判定——失败行+exit 1（既有 warn 已含原因链，此处只补结果语义与退出码）；② spec-sync.js 清单 GET 超时按形态分档——全量（无 since）取 120s、增量维持 10s（对齐 bundle 端点大小超时先例：大响应体独立档，非拍脑袋放大）；③ POST !res.ok 的 detail 提取扩一层——响应体 detail 字段含 op 级文本（path=…）时透传进 warn 行。三处共同根治「失败被成功横幅掩盖」：生产实证缓存漂移+慢链路+422 连坐三因叠加时，用户只见「0 个文件差异」，漏推不可见（2026-11-04 知识索引漏推确诊回执）。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

- `platform sync` CLI 退出语义变化：同步失败（ok:false）时退出码 0→1 并输出失败行（此前打成功横幅退出 0）——脚本化调用方可依赖退出码。
- `syncSpecTree`/`syncSpecTreeOnly` 内部返回值不变（ok:false 既有，仅调用方开始消费）。
- 清单 GET 超时：全量 10000ms→120000ms；增量不变。无新配置键（形态自判：URL 带 since 参数与否）。
- POST !res.ok 的 warn 文本可能多一段 detail（op 级错误文本）——纯附加信息。
- 无文件格式/端点签名变化。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

   超时档位由请求形态（带/不带 since）静态决定，无时序依赖；失败判定消费的是终态返回值，乱序不适用。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

   与既有同步并发语义一致（manifest 乐观锁/冲突分流不变）；本变更只改失败可见性与超时档，不新增写面。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

   超时熔断后缓存/lastSyncTs 不写（既有 fail 路径），中断重入语义不变；exit 1 只是 CLI 终态。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

   修改在 CLI 通用同步层，无仓路径/项目名硬编码；超时档与 detail 提取与具体平台实例无关（规约 00）。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：退出码语义变化破坏依赖「恒 0」的既有脚本（若有 CI 把 platform sync 当 best-effort 步骤）——权衡：失败静默正是本次生产事故根因（漏推 228 条知识不可见），可见性优先；best-effort 场景可 `|| true` 显式声明。放弃的方案：① POST 422 自动剔除无效 op 重试其余——422 的 rename-无内容根因在跨工作区污染行（平台侧事务），CLI 侧自动剔除有误删他端合法行的风险，先可见再由人工/平台侧清污；② 超时全面放大到 120s（含增量）——增量小响应 10s 是噪音闸门，放大后连接挂死场景每轮多等 110s；③ 新增 env 配置键调超时——形态自判已够（全量天然大响应），无需仓主配置面（零配置纪律）。
