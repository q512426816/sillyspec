# 设计记录（Design Record）— 2026-10-19-undeclared-cross-repo-probe

## 做法概述

消防工作区 4e9eb05b 的生产实证：thin 变更 design 无文件变更清单段时，主仓冻结面为空/只剩附件，真实代码在注册跨仓窗口内却零告警（2026-10-12..10-19 共 14 例）。既有空面门只拦「清单有未标注条目」；本变更在 patch 子步增加证据式探测：当清单没有任何 repo 标注且 local.yaml 注册仓非空时，逐仓调用既有 `collectRepoActual`（cross_baselines 3c 档）看窗口内交付改动，有则点名仓键/文件数并给规范标注三选一指引。探测只读、advisory 不阻断；纯文档/单仓/零改动零输出。顺带清理上一变更遗留的死变量 `patchTextPath`（评审 P3）。

## 接口契约

- 无新命令/端点/文件格式；`flow done` 新增一条 advisory 输出（仅命中形态）。
- 复用既有导出：`loadRegisteredRepoKeys`（scope-audit.js）、`collectRepoActual`（cross-repo-reconcile.js）、`filterDeliverableFiles`（worktree-apply.js）——均为只读采集，无签名变化。
- 探测异常逐项 fail-soft（单仓失败跳过、整体失败不阻断），不新造阻断面。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？
   窗口以 flow start 记录的 `cross_baselines` 为锚（首写者胜）；锚缺失时 collectRepoActual 回退既有 B/C 档。迟到提交只要落在窗口内即被探测到；探测在收口时点一次性执行，无事件序依赖。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？
   探测只读（git 查询），无写路径；与并行会话的竞争只影响「窗口内是否看到未提交改动」——文案已写明「疑似（未提交面可能含并行会话改动，请人工确认归属）」，advisory 不阻断，误报代价=一次人工确认。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？
   探测失败不影响 patch 子步状态机（fail-soft）；命中只打日志不写状态，重入可重复执行（幂等）。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？
   仅读取当前 specBase 的 local.yaml 注册表与各注册仓；未注册仓不在探测面内；单仓工作区（注册表空）零触发。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：未提交面无法归属，并行会话在注册仓的 WIP 可能被点名为「本变更未标注交付」——故只做 advisory 且文案标注「疑似/人工确认」，不做阻断。放弃方案：①按文件类别判定「仅脚手架面」（类别表会随工具演进漂移、误伤合法 skill 变更，且生产实证的 `.codex/**` 不在旧分类集内）——改用真实窗口 diff 作证据；②升级为阻断+签收——跨仓交付是该工作区常态，阻断等于对常态路径收税，且探测本身可能受并行 WIP 干扰，宁 advisory。
