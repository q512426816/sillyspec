# 设计记录（Design Record）— 2026-10-13-extract-head-guard

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

改 src/flow-draft.js extractSuccessCriteria 的续行合并循环：当前行命中 SECTION_HEAD_RE（成功标准/验收标准/动机/背景等节标题）时无条件独立成行、不并入上一行。缺陷机理（本会话自身实证）：前置行（动机等）行尾出现未闭合全角左括号 → needsContinuationMerge(prev) 判真 → 节标题行被并入动机行；合并行以冒号收尾再次触发合并 → 雪崩吞并其后全部条目行 → 提取 0 条、flow start 清晰度门误拒。为什么用「当前行守卫」而不是改 needsContinuationMerge 本体：吞标题是「当前行是结构边界」这一属性，与 prev 是否残缺无关——改本体（去括号判定）会破 R17 的括号跨行并回；节标题即使 prev 残缺也应另起一行（结构性事实）。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

extractSuccessCriteria（flow-draft.js 导出，flow start 清晰度门消费）行为变化：节标题行不再被续行合并吞入上一行——含未闭合括号动机的输入从提取 0 条变为正常提取。needsContinuationMerge 本体不动；SECTION_HEAD_RE 已有常量复用无新导出；无命令/端点/文件格式变化。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

成立。守卫是「当前行是否节标题」的纯行属性判定，与行的相对顺序无关；合并循环仍是逐行状态机、同输入同输出。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

纯函数零写面；extractSuccessCriteria 无共享状态，调用方（flow start）单次调用。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

安全。无状态机、无落盘；提取幂等。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

不会。改动限于该提取器的合并判定；消费方含 flow start 清晰度门（flow.js:757）与 draftAll/redraft 回提（flow-draft.js:899/1112/1124）——行为变化仅限「节标题被吞」的病理输入，各消费方增量语义一致。次生影响：无前缀裸行「背景」等出现在条目流中时，此前可能被并入残缺上一条、现在独立成行并触发节切换——更符合结构语义，属预期行为微调。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：守卫误伤——某条标准/内容行恰好整行形如节标题（如裸行「需求」）。此类行在受控输入里极罕见，且语义上它就是节切换意图（提取循环对节标题行的后续处理与守卫前独立成行时一致）。缓解：draft-continuation 既有 4 用例（括号跨行并回/悬空冒号并回/## 标题/分号斜杠不拆）+ 新增守卫用例全绿钉死。试过放弃的方案：①修 needsContinuationMerge 去括号判定——破 R17 括号跨行并回（动机换行拆条的原始修复），方向反了；②只在节检测正则上放宽（允许前缀污染）——吞并仍发生，条目行依旧被并成一行，治标不治本；③对 0 条提取的报错加特判提示——体验补丁不治病灶。均否。
