## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

两类改动：① 教学面——7 处分号内联教学（command.js status 空态 / flow.js 变更名重试 / index.js quick 退役 / worktree-guard.js 三处 / brainstorm.js 转轻量建议）统一改为含真实换行的可照抄多行实例（`成功标准：` 独立行 + `- <可验证标准>` 条目行），flow.js 清晰度门 ② 引导与 flow 用法行同步补实例/口径；② 模板面——flow-draft.js design 模板教学措辞强化为「问题行原样保留（勿删勿改勿替换），答案另起一行写在问题行下方」，并把实证计数从两度更新为三度、补「答案整块替换问题原文」失败模式。实例可照抄的依据：extractSuccessCriteria 逐行 trim（flow-draft.js:133）容忍展示缩进，`成功标准：` 独立行 + `- ` 条目行即过门——选择直接给实例而非改提取器，因为提取器语义（独立行门）是对的，缺口在教学侧。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

无函数签名/文件格式变化。CLI 输出面变化：status 空态引导、flow 变更名重试提示、quick 退役引导、worktree-guard 三处 stage 提示、brainstorm 转轻量建议、flow 清晰度门 ② 引导、flow 用法行输出，由单行分号描述形态变为含多行可照抄实例的输出（行数增加）；worktree-guard 提示数组 STAGE_HINTS 元素数增加（join('\n') 渲染不变）。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

不适用——改动是静态输出文案与模板教学文本，无输入事件流。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

不适用——仅 console 输出路径与模板字符串常量；唯一落盘面是 design.md 生成（既有 flow start 串行协议不变）。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

不适用——教学文案随代码分发，无运行时状态；已生成的旧 change 的 design.md 不回填（新措辞只对后续 flow start 生效）。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

不适用——实例文案为通用占位形态（<动机与背景>/<可验证标准>），不引用本仓状态；多实例输出一致。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

风险：多行教学使部分命令输出变长（worktree-guard 拦截提示从 ~9 行变 ~11 行）；terminal 折行下实例可能视觉粘连——接受，实例行保持短行、缩进区分。另一风险：教学实例字面与本变更测试断言耦合，未来改教学须同步测试——这正是断言的目的（锁可照抄性），可接受。试过但放弃：改 extractSuccessCriteria 使分号内联形态也过门——放弃理由：内联形态无法区分「动机句」与「标准条目」，放宽会把动机文本误收为标准，门语义受损；教学侧给实例是更小且语义正确的修复面。
