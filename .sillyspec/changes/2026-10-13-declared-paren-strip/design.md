# 设计记录（Design Record）— 2026-10-13-declared-paren-strip

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

三层修复，全部在解析/对账侧，不改冻结件生成器：①src/change-list.js 列表分支——括号注记剥除前置于冒号剥：先把行尾完整的全/半角括号组（含「（交付：说明）」内嵌冒号形态）剥掉，冒号剥只在剥完后的裸行上找真「路径：描述」形态（现序先剥冒号，冒号落在括号内把行砍成未闭合残片——缺陷档案实证形态）；②normalizePath 增未闭合尾括号残片剥除（trailing 开括号到行尾），闭合剥既有行为超集；③src/flow-parity.js buildThinSnapshotRows 兜底合并——declared 行 path 剥残片后与实际行同路径时：实际行 verdict 升 planned（归因更准）、占位行不补、totals 按唯一路径计。为什么三层：①治本（新解析不再产残片）、②治漏网（表格 cell 等其他入口的残片形态）、③治后果（任何来源的 declared/实际同路径分叉在快照层并回单行——消费方 join 口径干净）。存量归档件零回填（审计冻结原则）。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

normalizePath（change-list.js 导出）行为扩展：trailing 未闭合全/半角括号剥除（闭合剥超集，消费方含表格 cell/列表项/比较面同源生效）；_parseFileListDetailed 列表分支内部顺序调整（剥括号前置）；buildThinSnapshotRows（flow-parity.js 导出）增兜底合并。无新命令/端点/文件格式。行为变化：污染写法清单的解析产物从脏路径变干净路径；收口 scopeAudit 从双行变单行、totals.files 不虚高——存量归档件不动。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

成立。剥除是行尾后缀的确定性正则（完整括号组优先、残片兜底），与行的出现顺序无关；合并层在快照构建时一次性判定（剥残片后的精确等值匹配，非模糊相似度），无顺序依赖。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

纯解析/纯函数改动零写面新增；buildThinSnapshotRows 本就收口时点单次调用，无并发面变化。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

安全。无状态机参与；收口中断重入时快照重算幂等（同输入同输出）。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

不会。剥除只作用于 declared 面文本（design 清单），实际面（git numstat）不经 normalizePath；合并层只在主仓 rows 内做精确等值并归，跨仓行（crossRepo）走既有覆盖判定不动。存量归档件零回填（读取侧 flow diff 原样呈现历史冻结数据——缺陷档案已在平台仓记录该形态）。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：剥括号误伤真含括号的仓库路径（目录/文件名带括号，Windows 偶见）。缓解：只剥 trailing 后缀组（路径中段的括号不动）且需紧邻行尾；此类路径在仓内属病态命名，声明清单书写规范本就要求裸路径。次风险：合并层的等值匹配放过「同前缀不同文件」（a.ts 与 a.ts（x 残片剥后=a.ts 同值——正是要合并的形态；a.ts（x（y 双残片——剥两次需循环；实现循环至稳定）。试过放弃的方案：①只修解析不 加合并层——表格 cell 等其他入口的残片仍会产双行，消费方口径仍脏；②pathMatches 前缀容差合并——前缀匹配会把 a.ts 与 a.tsx 误并，必须精确等值；③存量归档件回填——违背审计冻结原则，读取侧如实呈现历史。均否。
