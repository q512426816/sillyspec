# 设计记录（Design Record）— 2026-10-23-fr-regress-default-off

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

只翻 readFrRegressCap 的返回语义（缺省/坏值/不可读：null→0；新增 all 值→null），组面消费点一行不改——缺省路径天然走 off 帽，all 走无帽，天然零分叉。披露行文案补开启指引（N/all）；动态子集信息行与 flow start 横幅测试面文案按实际组面如实描述（FR 层未进面不宣称含它）。夹具适配只动确实需要旧行为的 fr-priority-overlap（显式 all 留痕）；本仓 local.yaml 移除键收敛到缺省。这是用户对产品的缺省裁决（原话「默认就不跑，不用配置，配置可以开启」），版本升级即变脸——由 release notes 承载披露，想要旧网的仓一行 all 恢复。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

readFrRegressCap 返回语义 v2（缺省/坏值/不可读→0；off→0；N→N；all→null）；applyFrRegressCap 与组面消费点零改动。local.yaml 键取值域增 `all`。动态子集信息行/披露行/flow start 横幅测试面文案更新（如实反映缺省）。本仓 local.yaml 移除键。CLI 子命令面零变化。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

成立：键每轮组面时点重读（无缓存），all/N/off 与缺省的切换下一轮收口即生效；缺省路径与键路径同一消费点，无两套时序。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

读取 fail-soft 到新缺省 0（off）——与并行会话写配置竞态的最坏退化方向=少跑（保守），无写写冲突（本变更零新增写盘）。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

安全：缺省翻转是纯读取语义变更，无状态迁移；升级前后同仓行为差异由键控制（all 恢复），中断重跑幂等。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

不串台：键仓级；缺省翻转随 CLI 版本走（升级即变），各仓可用 all 钉住旧行为——版本兼容出口显式存在。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：升级即变脸——存量消费仓收口实测面突然变小，若某仓的 FR 层实际在抓回归，本地绿 CI 红的次数上升。对策：①缺省跳过恒打披露行+开启指引（每轮可见发生了什么、怎么恢复）；②all 一行恢复旧行为；③release notes 明示 breaking；④CI/pre-push 全量门兜底不变。放弃方案：①保留旧缺省+文档宣传新键（变更 6 已是此形态，用户明确否决——配置摩擦让默认慢路径永存，弃）；②按仓脸肥程度自动缺省（CLI 猜策略违反显式治理，弃）。
