# 设计记录（Design Record）— 2026-10-14-patch-refreeze-missing-artifact

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

在 `src/flow.js` patch 子步的既有漂移检测块前加一层**冻结件存在性复查**：`substeps.patch === 'done'` 时先查 `change-patch.json` 与 `change.patch` 是否在场，缺任一件 → 告警「冻结件缺失」并置 `drifted=true`（`drift=null`），进入既有漂移同款的 review 处置与 `driftRefreeze` 流（重冻结在当前 HEAD）。缺基面（无冻结 head 可比对）无法判 governance-only，review 未锚定时 fail-safe 走隔离重评。原「漂移检测失败 catch 吞掉 → 幂等跳过」的分支仅剩「json 在场但损坏」一种输入（本变更不改其 fail-safe 语义，见风险）。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

- 无新增导出/无签名变化：纯 `flow.js` patch 子步内部控制流增密。对外可见行为变化仅一条——「子步 done + 冻结件缺席」从静默跳过变为告警 + 自动重冻结（含 review 处置提示语）。
- 既有路径零变化：两冻结件在场时，漂移检测、anchored 保留、governance-only 保留、隔离重评、quarantineOk 失败回退跳过，全部逐字节保留。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

1. 乱序/迟到到达：存在性复查是重入时点的纯读判定，无时序假设；缺件与「重冻面 HEAD」之间若有并行提交，重冻结自然锚定更新面（与 --refreeze 手动语义一致）。
2. 并发写：重冻结走既有 writeAtomicSync 原子写；两冻结件「一件在场一件缺席」的中间态（写盘中断）由任一缺席即触发重冻覆盖。
3. 切换/生命周期：隔离 rename 失败回退幂等跳过（quarantineOk 语义原样保留），不留半套状态；review 标记重置的双故障边界注释原样保留。
4. 作用域：仅影响 flow done patch 子步重入路径，quick 通道已退役不涉及；跨仓（register-repo）冻结面本就不在扫描范围。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：缺件重冻锚定当前 HEAD，若窗口内存在本变更后缀提交但冻结件已缺，漂移无法检测（旧冻结 head 不可知）→ review 未锚定时隔离重评兜底（宁可多评），review 已锚定时结论对当前面有效——两条路都收敛到「审计件与评审对象一致」。放弃方案 A（catch 分支里对 ENOENT 特判重冻）：json 损坏（非 ENOENT）同样产「归档无冻结件」，但「在场即信任」与「缺失即重建」混在一个 catch 里语义含糊；显式前置存在性检查意图更清晰、可单测。放弃方案 B（artifacts/ledger 等其它子步一并做存在性复查）：本次缺陷实证面只有 patch 冻结件，其它子步产物（如 ledger 回执）有各自回填机制，一刀切扩面会放大回归风险——留作后续按同模式逐子步治理。
