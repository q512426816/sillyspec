## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

在 `src/run/command.js` 只读短路的空态分支（`!progress` 时）原句之后追加两行静态引导输出：一行给轻量跑道起步命令（`flow start --change <名> --input "<动机；成功标准：每行一条>"`），一行给需求不明时的 brainstorm 备选。纯输出层追加：不引入任何状态读取、IO 或新依赖，exit 0 与「只读不建变更」语义原样保留——空态的定义就是无数据可读，静态文案是最小且最稳的方案。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

无函数签名变化；对外可见变化仅一处：`sillyspec status` / `sillyspec run status` 在无进度数据空态的 stdout 由 1 行变 3 行（原句 + 两条引导）。有活跃变更时的展示路径零改动。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？
   不适用：改动点是同步 console 输出，位于进程退出前的单一分支，无事件序参与。
2. 并发写：两个执行体同时操作同一数据/文件会发生什么？
   不适用：只读短路路径本身零落盘（该分支的既有语义），引导输出不引入任何共享可变状态；多会话同时跑 status 各自打印，互不干扰。
3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？
   不变：`process.exit(0)` 与原分支一致，输出后即终止，无中间态。
4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？
   引导文案为通用命令示例（`<YYYY-MM-DD-名>` 占位符），不引用本仓路径、变更名或机器标识，任何仓库打印内容一致，无串台面。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：文案与未来选道入口漂移（若 flow start 参数形态变更，引导文案会悄悄失效）——以 FR-01 断言「含 flow start 子串」钉住最小锚，入口大改时测试会显式红。放弃的方案：读取本仓 spec 状态做「智能下一步建议」（如检测 .sillyspec/docs 存在性给不同建议）——空态分支的定义就是 progress 无数据可读，智能层没有可靠输入反而引入误判面，且跨仓语义不通用，故弃。
