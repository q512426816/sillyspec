# 设计记录（Design Record）— 2026-10-07-tick-timing-first-commit

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

flow.js 哨兵「勾选时点」块一处改动：tasksIn 从 `git log -n 1 -- path`（最近一次提交）改为 `git log --reverse --format=%h -- path` 全 history 取首行（首次提交），空输出（untracked）归 null 走原分支。选 --reverse 首行而非 rev-list|tail 是单次 gitQuiet 调用内可完成、参数面与既有钉同构。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

cmdFlowDone 内部时点判定锚定变化；无函数签名/命令/文件格式变化。用户可见行为：渐进提交形态不再出「一把勾模式」advisory。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

不适用：git history 只读判定，无事件序依赖。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

不适用：只读 git 查询；收口单写者上下文。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

不适用：判定幂等（每次 done 重算），中断重入语义不变。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

不适用：git 查询按 cwd 与路径参数限定，无跨仓面。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：超大 history 下 --reverse 全量列举的耗时（路径限定后通常个位数提交，实际无感）。试过放弃：`git rev-list | tail -1`——需二次管道/字符串处理且 rev-list 无 --format；放弃。
