# 设计记录（Design Record）— 2026-10-10-release-3-32-4

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

纯发布变更（复刻 2026-10-09-release-3-32-2/3 惯例），零代码交付：版本面（package.json=3.32.4 + R5 锚）已在此前变更落地（af6fd5ac bump、666a90f8 补 R5 锚），本变更只做发布三件事——推送、钉扎通道发布、双核验留痕。发布环境 DNS 被劫持（registry.npmjs.org 国内解析指向停放 IP，前两版实证），publish 与核验都必须经腾讯 DoH（1.12.12.12 直连 IP 查询，不经本地 DNS）解析真实 Cloudflare IP，再用 NODE_OPTIONS --require 注入 dns-pin.cjs 做进程级 dns.lookup 钉扎（仅本进程、零系统改动）；钉扎 IP 在发布前重新解析刷新（IP 会轮换，3.32.3 用的 104.16.19.35 不保证仍有效）。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

   成立。发布顺序固定：先 push 后 publish——npm 包消费方按 registry 取包，与 git 远端无顺序耦合；核验在 publish 返回成功后进行，传播延迟用轮询等待（前两版约 3 分钟）。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

   npm registry 对同名同版本发布原子拒绝（403 EPUBLISHCONFLICT）——重复发布天然被挡；本地 main 为独占工作区，无并行提交竞争面（并行会话的在途文件不进本次推送面）。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

   中断点幂等：push 可重跑（远端已有则空推）、publish 失败可重试（版本冲突=已成功的证明）、核验可重跑；最坏半态（已发布未留痕）由 requirements 核验留痕补写收口，不产生不可恢复状态。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

   不会。DNS 钉扎仅注入本发布进程（NODE_OPTIONS 进程级），不影响系统解析与他进程；发布身份 npm whoami=qy0604 唯一；github.com 解析不受劫持影响（前两版实证），推送不经钉扎。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：钉扎 IP 失效或 DoH 通道本身也被劫持（阿里 DoH 已沦陷，腾讯 DoH 是当前唯一可信通道）——IP 直连腾讯 DoH 端点（1.12.12.12）不依赖被劫持的域名解析，通道存活由发布前预核验（钉扎 npm view 返回真实 latest=3.32.3）先行证明：预核验失败即停，不带病发布。试过放弃的方案：① 改 hosts 文件钉扎——动系统配置，污染面大于进程级注入，放弃；② 用未钉扎 npm view 的结果做核验——劫持环境下数据不可信（本次实测返回污染值 3.32.2），放弃；③ 跳过核验直接发布——违背 3.32.2/3.32.3 惯例（latest 双核验是发布 FR），放弃。
